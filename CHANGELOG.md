# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.2.1] - 2026-10-11

### Added
- **Reset Record**: Each counter and integration records when and why its total was last cleared: a new period, a change of time zone that jumped over a boundary, the followed path falling, or a request. For a followed path the record holds the value it fell from, the value it fell to and the source of the lower value. The status page shows the record under the entry, the status route reports it as `lastReset`, and it is saved with the total. A start time that was replaced without clearing the total, after a clock correction, is recorded the same way as `sinceCorrected`. A total that starts again at an unexpected time now states the reason.
- **Zone Change Record**: The status page states the last change of the followed time zone, or of the path it is read from, with the time and both zones. The status route reports it as `timeZoneSource.lastChange`.
- **Plugin Start Time**: The status page and the status route (`startedAt`) state when the plugin last started.

### Fixed
- **Saved Totals Missing After a Restart**: A counter or integration restored from the state file showed "Waiting" and published nothing until its input sent a value, whatever its stale setting. After a server restart with an engine switched off, a daily engine total therefore disappeared until the engine was next switched on. A restored total is now the entry's value from the start. It is shown with the text "No value on ... since the plugin started": as stale, and published when the entry is set to keep publishing its last result; or, for an entry with a stale timeout of zero, as publishing. It is passed to the entries that read it whenever it is published. It still rolls over at its period boundary while the input stays silent. One pass runs as soon as the plugin starts, so a boundary that passed during downtime is applied before the status is first read.
- **Chained Counter Missing a Boundary After a Restart**: A counter that reads another entry's total now receives a restored total that is being published, and the zero that follows a boundary passed during downtime. Before, it heard nothing until the restored entry's own input had spoken, and then counted the difference to the value from before the stop. Its total after such a restart now matches what a boundary seen live produces.
- **Total Cleared by a Value the Server Still Held**: The server keeps the last value of every source that ever wrote to a path and replays them all, oldest first, when the plugin starts. Where a device had appeared under two source names, a total that resets when a path falls saw the old name's last value followed by the current one and was cleared at every plugin start; a period counter on such a path counted the difference. One held value per path is now used at start-up: the one the server itself reports for the path, or the held value with the newest time stamp. The paths that carry the ship's time zone are treated the same way, so an old source's zone is no longer recorded as a change at every start.
- **Old Values Read as New**: The server can also hand over a held value while the plugin runs. A value from a source other than the one last read is now ignored when it repeats exactly what that source sent before (same time stamp, same value), or, from a source not seen before on that path, when it is older than the value last read. Every value held at start-up counts as seen. A time stamp from the future counts as the moment of arrival. The zone tracker likewise ignores a value from another source that is older than the one it holds for a path. The status page counts the ignored input values and names the last one; the status route reports them as `outdatedValues`. Values from the source last read are never ignored, so a replayed log is still read.
- **List Descriptions Shown Twice ([signalk-server#3143](https://github.com/SignalK/signalk-server/issues/3143))**: The settings form showed the description of the Formulas, Period counters and Integrations lists twice, once above each heading and once below it. The Admin UI of Signal K server 2.33 prints a list's description in both places, so the three lists no longer carry one; the plugin's description at the top of the form says what each list holds.

## [0.2.0] - 2026-10-10

### Added
- **Ship's Time Zone**: Day, week, month and year boundaries can follow the time zone the vessel keeps, read from Signal K. The standard paths `environment.time.timezoneRegion` (a zone name) and `environment.time.timezoneOffset` (hours and minutes as one number) are read by default, so a plugin such as Ship's Time is followed without any setup. A name is preferred to an offset; an offset published later than the name, and disagreeing with it, takes over. This is the default for new and existing installations; with nothing published on those paths the behaviour is as before. An installation where Ship's Time is still at its default of manual mode and offset zero will follow UTC until that plugin is configured.
- **Configurable Paths for the Zone**: The two paths can be changed, for installations where custom code or another plugin publishes the zone elsewhere. Either path accepts a zone name, a fixed offset written as text, or the specification's number form.
- **Zone Changes Follow the Calendar**: A total belongs to a calendar date and is cleared when a later date begins, never twice for the same date. A change of zone therefore behaves like a daylight saving change: going east over a boundary starts the new period at once, and going west back over a boundary carries the period on until the next one begins. The status page explains either case on the entry concerned.
- **Remembered Zone**: The last zone followed is saved with the totals and used after a restart until the source publishes again, so a restart cannot move a day boundary.
- **Time Zone List**: The time zone setting is now a list holding the server's own zone, UTC, the fixed offsets from UTC-12:00 to UTC+14:00 including the part-hour ones, and the zone names the runtime knows. Fixed offsets are new; they do not follow daylight saving, and the list says so. A zone saved earlier that the list does not hold is added to it, so opening and saving the form never replaces it.
- **Zone in the Status**: The status page states the zone in use and where it comes from, the status route reports the same as `timeZoneLabel` and `timeZoneSource`, and the plugin's status line names a followed zone. A value on a followed path that is not a zone is reported on the status page.
- **Full Changelog Link in Releases**: Each GitHub Release now ends with a link to the comparison with the previous version.

### Changed
- **Time Zone Setting**: The setting is renamed "Time zone when none is published" and is the fallback when the ship's time is followed. A zone name saved by version 0.1.0 keeps working, and an empty value still means the server's own zone. To keep a fixed zone regardless of what is published, "Time zone for day boundaries" is set to "Always use the time zone chosen below".
- **State File**: Each period total now records the calendar date of its period and the zone that date was read in, next to the start instant, and the file holds the last zone followed. State written by version 0.1.0 is taken over with its totals, and the file remains readable by 0.1.0.
- **Release Workflow**: The release action moved to `softprops/action-gh-release@v3`, which runs on Node 24.

## [0.1.0] - 2026-10-10

### Added
- **Formulas**: An entry type that publishes the result of an expression over any number of live paths and constants. Each input path is given a short name, because paths contain dots and dashes that an expression would read as operators. Expressions are parsed by `expr-eval-fork` with assignment, function definitions, arrays, string concatenation and property access switched off, and are never passed to JavaScript's `eval`.
- **Period Counters**: An entry type that publishes how much a running total has changed since the start of the day, week, month or year, or since a manual reset. It can count increases only, decreases only (a falling tank level becomes consumption) or the net change, with a smallest-change setting that keeps sensor ripple out of the total.
- **Integrations**: An entry type that adds up an input over time. One mode multiplies the value by the elapsed time (power into energy, flow into volume); the other adds up the time the input spends above a threshold (engine running time, time a switch is on). A regularly sampled input is joined by straight lines between values, and an input with a stale timeout of `0` is held at its last value and extended every second.
- **Selectable Resets**: Period boundaries are computed in a configurable IANA time zone with a configurable start of day and first day of the week, including on the 23-hour and 25-hour days of a daylight saving change. As an alternative, a total can reset whenever another path's value falls, so that a calculated daily total keeps step with a device that resets its own daily figure at its own time.
- **Chaining**: An entry can use another entry's output as an input. Entries are calculated in dependency order, each once per incoming update, so values that arrive together are applied together. A reset, a period rollover, a missing result and a stale input all reach the entries downstream. Entries that feed each other in a loop are refused with a message while the remaining entries run.
- **Stale Input Handling**: A per-entry stale timeout, with a per-entry choice between stopping publication and continuing to publish the last result. A formula is not recalculated while one of its inputs is stale. For integrations, a gap longer than the timeout is left out of the total by default and can optionally be bridged with the last value.
- **State Persistence**: Totals, baselines and period starts are saved to `state.json` in the plugin's data directory every 30 seconds when changed, on stop and at every reset. The file is written to a temporary file, flushed to disk and renamed over the previous one, so an interrupted save leaves the old file or the new one, and it is rewritten in place, so it does not grow.
- **Clock Safety**: Elapsed time is measured on a monotonic clock, and period resets pause while the system clock reads earlier than 2024 or earlier than the last saved state. A computer without a clock battery that boots at 1970 therefore neither resets its totals nor counts the correction as elapsed time. A clock that is wrong but plausible cannot be detected.
- **Unit Metadata**: Each output path is announced with its unit, display name and description, so the Data Browser and instrument displays can label it.
- **Status Page**: A page under Webapps lists every entry with its current value, state, explanatory message and the time counting began, and offers a reset button with a confirmation step for counters and integrations. Values are shown in an everyday unit with the published SI value beneath.
- **HTTP Interface**: `GET /plugins/signalk-calc-paths/api/entries` returns every entry's status, and `POST /plugins/signalk-calc-paths/api/entries/{output path}/reset` clears one total. Reading is open to any logged-in user and resetting to read/write and admin users through the server's per-route access levels; on servers without that feature both routes stay admin-only. An OpenAPI description is registered with the server.
- **Automated Tests**: A test suite covering period boundaries across time zones and daylight saving changes, formula parsing and its restrictions, every counter and integration mode, chained entries, restarts, clock faults, configuration checking, state storage and the plugin's interaction with the server API, plus an end-to-end check that runs against a live Signal K server in CI.
